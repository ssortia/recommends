# Локальный стенд в копии репозитория (git worktree)

**Цель:** поднять рабочий стенд в любой копии репозитория одной командой и держать несколько
копий запущенными одновременно, не мешая друг другу.

Архитектурные решения за этой схемой зафиксированы в [ADR-016](../adr/016-worktree-local-dev.md).

## Как устроен стенд

| Что              | Значение                                                                  |
| ---------------- | ------------------------------------------------------------------------- |
| Postgres         | один общий контейнер на порту `5444`, своя база `recommends_<slug>`       |
| Порты            | основной checkout — 3000/3001, копии — первая свободная пара от 3010/3011 |
| Адрес в браузере | `http://<slug>.localhost:<WEB_PORT>`                                      |
| Серверные адреса | `http://127.0.0.1:<PORT>`                                                 |
| Процессы         | API и web локально через `pnpm dev`; в Docker остаётся только БД          |

`slug` — имя папки worktree. Разные имена хостов нужны потому, что cookies не изолируются по
номеру порта: на общем `localhost` вход в одной копии сбрасывает сессию в другой.

Серверные адреса зафиксированы на `127.0.0.1` намеренно: `<slug>.localhost` резолвится в `::1`,
а API слушает только IPv4.

> **Границы схемы.** Она распространяется на локальный запуск (`pnpm dev`) и на сервис `db` в
> compose. Полный стек `docker compose up` (сервисы `api` и `web`) живёт по своим правилам: у
> сервиса `api` жёстко задан `DATABASE_URL: …@db:5432/recommends`, и значение из `.env` его не
> переопределяет. Из `.env` compose берёт только порты публикации на хосте.

## Предварительные требования

| Инструмент | Минимальная версия | Проверить   |
| ---------- | ------------------ | ----------- |
| Node.js    | 22                 | `node -v`   |
| pnpm       | 9                  | `pnpm -v`   |
| Docker     | 24                 | `docker -v` |

- Копия репозитория создана (`git worktree add ../<имя> <ветка>`) и находится в отдельной папке —
  её имя станет slug'ом стенда.
- Общий контейнер Postgres запущен (обычно его поднимает основной checkout).

## Шаги

### 1. Убедиться, что контейнер Postgres запущен

Команда подготовки не поднимает БД сама — так исключается случайный второй контейнер.

```bash
docker compose ps db
```

Если контейнера нет — поднять его **из основного checkout**:

```bash
docker compose up -d db
```

Ожидаемый результат: сервис `db` в статусе `healthy`, порт `5444` слушается.

### 2. Установить зависимости

```bash
pnpm install
```

### 3. Подготовить стенд

```bash
pnpm setup:worktree
```

Команда:

1. определяет slug по имени папки и имя базы `recommends_<slug>`;
2. подбирает свободную пару портов (свободную и в системе, и среди `.env` соседних worktree);
3. генерирует `.env` из `.env.example`;
4. собирает `@repo/types` и `@repo/utils`, затем выполняет `db:generate`, `db:migrate`, `db:seed`;
5. печатает адрес стенда и учётные данные seed-пользователя.

Ожидаемый результат — примерно такой хвост вывода:

```
Стенд готов.
  Запуск:  pnpm dev
  Адрес:   http://sandworm.localhost:3010
  API:     http://127.0.0.1:3011
  Вход:    admin@example.com / admin123456
```

Повторный запуск `.env` не трогает: команда печатает текущие параметры и выходит. Перегенерация —
только по явному флагу:

```bash
pnpm setup:worktree --force
```

> `--force` перезаписывает `.env` целиком и заново прогоняет миграции и seed. Локальные правки
> `.env` при этом теряются.

### 4. Запустить стенд

```bash
pnpm dev
```

Порты берутся из `.env` (`API_PORT` и `WEB_PORT`), а не из захардкоженных значений: оба
приложения запускаются через `dotenv-cli` с корневым `.env`. Без `.env` web стартует на дефолтном
3000, а API падает на валидации переменных — это ожидаемое поведение и причина существования шага 3.

## Проверка

### 1. Стенд отвечает

```bash
curl http://127.0.0.1:<API_PORT>/health     # {"status":"ok",...}
curl -I http://127.0.0.1:<WEB_PORT>/        # 307 на /login
```

Swagger — на `http://127.0.0.1:<API_PORT>/api/docs`.

### 2. Вход в браузере

1. Открыть `http://<slug>.localhost:<WEB_PORT>` (именно slug-хост — так сессия не пересечётся с
   другими копиями).
2. Войти под `admin@example.com` / `admin123456`.
3. После входа — редирект на дашборд.

### 3. Подтвердить email seed-пользователя

Seed создаёт админа с `emailVerified: false`, поэтому страницы `/sources` и `/preferences` сразу
после входа отдают `403` от `VerifiedGuard`. Как это обойти — в «Частых проблемах» ниже; без
этого шага основные сценарии продукта не проверить.

### 4. Письма — в логах API

При `MAIL_TRANSPORT=json` (значение по умолчанию) письма никуда не уходят, а сериализуются в JSON
и логируются:

```
LOG [MailerService] { msg: 'Email sent (jsonTransport)', message: '{...тело письма со ссылкой...}' }
```

Ссылку для верификации или сброса пароля можно скопировать прямо из вывода `pnpm dev`. Удобный
способ вытащить её из лога:

```bash
grep -o 'verify-email?token=[A-Za-z0-9]*' <файл с логом API> | tail -1
```

### 5. Изоляция сессий между копиями

Войти на `http://<slug>.localhost:<WEB_PORT>`, затем в том же браузере открыть
`http://localhost:<WEB_PORT>` — там будет редирект на `/login`, а возврат на slug-хост сессию
сохранит. Это подтверждает, что cookie next-auth скоупится по имени хоста: две копии на разных
slug-хостах не пересекаются.

### 6. Прогон e2e на нестандартных портах

Тесты менять не нужно — адреса читаются из переменных окружения:

```bash
pnpm --filter @repo/web exec playwright install chromium   # один раз

PLAYWRIGHT_BASE_URL="http://<slug>.localhost:<WEB_PORT>" \
PLAYWRIGHT_API_URL="http://127.0.0.1:<API_PORT>" \
E2E_RSS_FEED_HOST="127.0.0.1" \
pnpm --filter @repo/web test:e2e
```

Требования к стенду для e2e:

- API запущен с `NODE_ENV=test` — иначе недоступен test-only эндпоинт выдачи токена
  `GET /auth/__test/last-token`;
- для `e2e/telegram-source.spec.ts` API дополнительно перезапущен с
  `TELEGRAM_PREVIEW_BASE_URL="http://127.0.0.1:4310"` (значение кешируется `getEnv()` один раз при
  старте);
- `PLAYWRIGHT_API_URL` и `E2E_RSS_FEED_HOST` указывают на `127.0.0.1`, а не на slug-хост:
  запросы идут со стороны сервера и API слушает только IPv4.

## Частые проблемы

| Проблема                                                                    | Причина                                                                                                                               | Решение                                                                                                                                                                                                                            |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Запросы к API из браузера падают с ошибкой CORS                             | Зашли на хост, которого нет в `CORS_ORIGIN` (например, `127.0.0.1:<WEB_PORT>` или чужой slug)                                         | Заходить по адресу из `NEXTAUTH_URL`. Скрипт кладёт в `CORS_ORIGIN` два адреса — `http://<slug>.localhost:<WEB_PORT>` и `http://localhost:<WEB_PORT>`; другой хост нужно дописать туда вручную (через запятую) и перезапустить API |
| Запросы к `/_next/*` со slug-хоста отклоняются dev-сервером Next            | Хост не попал в `allowedDevOrigins`                                                                                                   | В `apps/web/next.config.ts` уже перечислены `localhost`, `127.0.0.1`, `*.localhost`; для нестандартного имени хоста добавить его туда                                                                                              |
| `pnpm setup:worktree` завершается с «Postgres недоступен на 127.0.0.1:5444» | Общий контейнер БД не запущен                                                                                                         | `docker compose up -d db` из основного checkout, затем повторить команду                                                                                                                                                           |
| `docker compose up -d db` падает с `port is already allocated`              | Порт `5444` уже занят общим контейнером другой копии — это и есть нужный контейнер                                                    | Не поднимать второй: копия использует уже запущенный. Проверить `docker ps --filter publish=5444`. Если порт занят посторонним процессом — задать `DB_HOST_PORT` в `.env` и поправить `DATABASE_URL`                               |
| Порт web или API занят при `pnpm dev`                                       | Пара портов занята другой копией или посторонним процессом                                                                            | `lsof -i :<порт>`; освободить порт либо перегенерировать `.env` командой `pnpm setup:worktree --force`                                                                                                                             |
| `403 EmailNotVerified` на `/sources` и `/preferences` под seed-админом      | Seed создаёт пользователя с `emailVerified: false`, а эти маршруты закрыты `VerifiedGuard`                                            | Запросить письмо и перейти по ссылке из лога (проверенный путь, см. ниже)                                                                                                                                                          |
| Баннер «email не подтверждён» не исчезает сразу после верификации           | Признак `emailVerified` зашит в access-токен                                                                                          | Перелогиниться (или дождаться обновления токена) — новый токен выпускается из свежего состояния пользователя                                                                                                                       |
| E2E падают при одновременном прогоне в двух копиях                          | Mock-сервер Telegram слушает фиксированный порт `4310` (`apps/web/e2e/telegram-source.spec.ts`), два прогона конкурируют за один порт | Гонять e2e только в одной копии за раз                                                                                                                                                                                             |
| E2E падают на выдаче токена верификации                                     | API запущен без `NODE_ENV=test` — test-only эндпоинт отключён                                                                         | Перезапустить API с `NODE_ENV=test`                                                                                                                                                                                                |
| API падает на старте с ошибками валидации env                               | `.env` не сгенерирован                                                                                                                | `pnpm setup:worktree`                                                                                                                                                                                                              |
| `docker compose up` (полный стек) работает не с базой копии                 | Схема worktree покрывает только локальный запуск и сервис `db`                                                                        | Это ожидаемо: у сервиса `api` жёстко задан `DATABASE_URL: …@db:5432/recommends`. Для стенда копии использовать `pnpm dev`                                                                                                          |

### Как подтвердить email seed-пользователя локально

Проверенный путь — через обычный флоу верификации, при `MAIL_TRANSPORT=json` (значение по
умолчанию) реальный SMTP не нужен:

1. Запросить письмо (эндпоинт публичный, отвечает `204`):

   ```bash
   curl -X POST http://127.0.0.1:<API_PORT>/auth/resend-verification \
     -H 'Content-Type: application/json' \
     -d '{"email":"admin@example.com"}'
   ```

2. В логе API (вывод `pnpm dev`) найти запись `MailerService` со ссылкой вида
   `http://<slug>.localhost:<WEB_PORT>/verify-email?token=...` и открыть её в браузере — страница
   `/verify-email` сама вызовет `POST /auth/verify-email`. Тот же токен можно отправить напрямую:

   ```bash
   curl -X POST http://127.0.0.1:<API_PORT>/auth/verify-email \
     -H 'Content-Type: application/json' \
     -d '{"token":"<токен из ссылки>"}'      # 204
   ```

3. Перелогиниться в браузере — признак `emailVerified` попадает в новый access-токен. После этого
   `/sources` и `/preferences` отвечают `200`.

Правка записи в БД напрямую (`UPDATE users SET "emailVerified" = true …`) тоже сработает, но
требует того же перелогина и обходит аудит-событие `EMAIL_VERIFIED` — предпочтительнее путь через
письмо.
