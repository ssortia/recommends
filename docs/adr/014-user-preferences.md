# ADR-014: Отдельная таблица `UserPreferences` для описания интересов

**Статус:** Принято
**Дата:** 2026-07-13

---

## Контекст

Issue #12 требует, чтобы пользователь мог описать свои интересы произвольным текстом — в будущем это описание будет использоваться AI-модулем оценки релевантности статей (пока не существует в кодовой базе). Помимо этого текстового поля, в ближайшем будущем ожидаются ещё как минимум два preference-поля: фильтрация по категориям (issue #13) и порог релевантности для AI-оценки (issue #14).

Модель `User` (`apps/api/prisma/schema.prisma`) на момент решения не содержит preference-полей. Нужно было выбрать, куда класть `interestsDescription` и последующие поля.

---

## Рассмотренные варианты

- **Поля напрямую в `User`.** Проще для одного поля, но `User` — модель аутентификации/профиля; по мере добавления #13 (категории) и #14 (порог релевантности) таблица разрасталась бы preference-полями, не связанными с сутью модели, и смешивала бы два разных домена (аккаунт vs персонализация подбора).
- **Отдельная таблица `UserPreferences` (1:1 с `User`).** Изолирует preference-поля в отдельном домене, под который уже сейчас закладывается место для #13/#14. Обратная связь `preferences UserPreferences?` в `User` необязательная — можно создавать запись лениво.

Выбран второй вариант.

---

## Решение

1. **Таблица `user_preferences`** (модель `UserPreferences`) — 1:1 с `User` через уникальный `userId` и `onDelete: Cascade`. Первое поле — `interestsDescription String? @db.VarChar(1000)`. Лимит 1000 символов — защита от злоупотребления и от чрезмерно длинных промптов для будущего AI-модуля.

2. **Ленивое создание записи.** `UserPreferences` не создаётся при регистрации пользователя — только при первом сохранении настроек (`upsert`). `GET /preferences` для пользователя без записи возвращает `{ interestsDescription: null }`, а не 404. Это исключает необходимость миграции существующих пользователей отдельным скриптом.

3. **Модуль `preferences`** (`apps/api/src/preferences/`) — repository/service/controller по образцу `sources` (ADR-007): `GET /preferences`, `PATCH /preferences` под `JwtAuthGuard` + `VerifiedGuard`.

4. **Задел под #13/#14.** Будущие поля (список интересующих категорий, порог релевантности) добавляются как новые колонки в ту же таблицу `user_preferences`, без создания новых таблиц и без изменения формы API-модуля.

---

## Последствия

### Положительные

- Preference-поля физически и логически отделены от аутентификационной модели `User`.
- Расширение под #13/#14 — это добавление колонок в существующую таблицу и полей в существующий DTO/Zod-схему, без структурных изменений.
- Ленивое создание записи не требует backfill-миграции для существующих пользователей.

### Отрицательные / компромиссы

- Каждое чтение preference-данных требует `JOIN` (или отдельного запроса) к `user_preferences` вместо чтения поля из уже загруженного `User`.
- Пока в таблице одно поле, отдельная таблица может выглядеть избыточной — оправдана только в свете уже запланированных #13/#14.
