# ADR-016: Локальный запуск нескольких копий репозитория (worktree) одновременно

**Статус:** Принято
**Дата:** 2026-09-21

---

## Контекст

Issue #31. Разработка ведётся в нескольких git worktree одновременно (основной checkout плюс
копии под отдельные задачи). До этого решения свежая копия не поднималась:

- ни `nest start --watch`, ни `next dev` не читали корневой `.env` — его подхватывали только
  скрипты `db:*` через `dotenv-cli`, поэтому API падал на валидации `env.ts`;
- порт Postgres в `docker-compose.yml` был захардкожен (`5444:5432`), и `docker compose up` во
  второй копии падал с `Bind for 0.0.0.0:5444 failed: port is already allocated`;
- порты приложений были захардкожены (`3000`/`3001`), две копии конфликтовали между собой;
- `next dev` читает порт из переменной `PORT` — той же, которую читает Nest, поэтому одной
  переменной на оба приложения не хватает;
- задача `dev` в `turbo.json` не имела `dependsOn: ["^build"]`, и на чистом checkout API стартовал
  раньше первой эмиссии watch-сборки `@repo/types`/`@repo/utils` и падал на отсутствующем `dist/`.

Дополнительные факты окружения, которые ограничивают решения:

- cookies не изолируются по номеру порта — вход в одной копии на `localhost` сбрасывает сессию
  next-auth в другой копии на том же `localhost`;
- `<slug>.localhost` резолвится через `getent hosts` в `::1`, а API слушает только IPv4
  (`app.listen` с адресом `0.0.0.0` в `apps/api/src/main.ts`);
- mock-сервер Telegram в e2e слушает фиксированный порт `4310`
  (`apps/web/e2e/telegram-source.spec.ts`).

---

## Рассмотренные варианты

### Изоляция базы данных

- **Свой контейнер Postgres на копию.** Полная изоляция данных и версии БД. Минусы: каждая копия
  занимает свой порт хоста и свой volume, растёт потребление памяти, появляются «забытые»
  контейнеры от удалённых worktree.
- **Один общий контейнер, своя БД в нём (выбрано).** Контейнер один — `recommends-db-1` из
  основного checkout на порту `5444`; каждая копия работает со своей базой
  `recommends_<slug>`. Изоляция данных та же, ресурсов меньше, нет конфликта портов. Минус:
  копии делят один инстанс Postgres — его падение или пересоздание volume задевает все копии, и
  версия Postgres общая.

### Выбор портов

- **Хеш от имени worktree.** Детерминированно и без сканирования, но коллизии хешей дают две
  копии на одной паре портов, а обнаруживается это только при запуске.
- **Первая свободная пара (выбрано).** Пара считается свободной, если её порты и не слушаются в
  системе, и не записаны в `.env` соседних worktree (список даёт `git worktree list`). Второе
  условие важно: две копии, подготовленные до первого `pnpm dev`, иначе получили бы одинаковые
  порты. Минус: порт копии не предсказуем заранее — его надо смотреть в `.env`.

### Адрес в браузере

- **`localhost:<WEB_PORT>` для всех копий.** Ничего настраивать не нужно, но cookies общие на
  весь `localhost` — вход в одной копии разлогинивает другую.
- **Слушать `::` в `main.ts`, чтобы slug-хост работал и для серверных запросов.** Отвергнуто:
  меняет поведение продакшена (API начинает слушать IPv6 везде) ради удобства разработки.
- **Slug-хост только для браузера (выбрано).** Браузерные переменные (`NEXTAUTH_URL`, `WEB_URL`,
  `NEXT_PUBLIC_API_URL`) указывают на `http://<slug>.localhost:<PORT>`, серверные (`API_URL`,
  `PLAYWRIGHT_API_URL`) — на `http://127.0.0.1:<PORT>`. Разные имена хостов разводят cookies, а
  фиксация `127.0.0.1` для серверной стороны снимает зависимость от порядка выбора семейства
  адресов (slug-хост резолвится в `::1`, API слушает только IPv4).

### Секреты в сгенерированном `.env`

- **Генерировать новые случайные секреты на копию.** Ближе к продакшен-практике, но ломает
  воспроизводимость (токены одной копии не подходят к другой) и усложняет сравнение `.env`
  между копиями.
- **Фиксированные dev-заглушки из `.env.example` (выбрано).** Те же значения, что и в примере,
  плюс guard в `apps/api/src/config/env.ts`, отклоняющий известные заглушки при
  `NODE_ENV=production`. Это сознательное отклонение от критерия issue #31 «генерировать новые
  секреты».

---

## Решение

1. **Единый источник переменных — корневой `.env`.** Оба приложения запускаются через
   `dotenv-cli`, как уже было сделано в скриптах `db:*`:
   - `apps/api`: `dotenv -e ../../.env -- sh -c 'PORT=${API_PORT:-3001} nest start --watch'`;
   - `apps/web`: `dotenv -e ../../.env -- sh -c 'next dev --turbopack --port ${WEB_PORT:-3000}'`.

   Раздельные `API_PORT` и `WEB_PORT` нужны потому, что `next dev` и Nest читают одну и ту же
   переменную `PORT`. Задача `dev` в `turbo.json` получила `dependsOn: ["^build"]` — API больше
   не стартует раньше сборки общих пакетов.

2. **Команда подготовки `pnpm setup:worktree`** (`scripts/setup-worktree.mjs`, чистый Node без
   зависимостей). Она определяет slug по имени папки worktree, подбирает свободную пару портов,
   генерирует `.env` из `.env.example`, затем последовательно выполняет сборку `@repo/types` и
   `@repo/utils`, `db:generate`, `db:migrate`, `db:seed` и печатает адрес стенда с учётными
   данными seed-пользователя (читает их из `apps/api/prisma/seed.ts`, чтобы не дублировать
   константы). Существующий `.env` не перезаписывается (перегенерация — только по `--force`), но
   остальные шаги идемпотентны и выполняются в любом случае: иначе повторный запуск после
   упавшей миграции печатал бы «успех», не доведя стенд. При `--force` пара портов из
   существующего `.env` сохраняется: иначе запущенный стенд копии выглядел бы как «порты заняты»
   и перегенерация молча увела бы копию на другую пару. Порт БД берётся из того же источника,
   что и `${DB_HOST_PORT}` в compose (переменная окружения → `.env` → `.env.example` → `5444`),
   поэтому его смена не разводит генератор и compose.

3. **Чистая логика вынесена** в `scripts/lib/worktree-env.mjs` (`toSlug`, `resolveDatabaseName`,
   `pickPortPair`, `buildEnvContent`) и покрыта тестами `node --test`
   (`pnpm test:scripts`, 17 тестов). В обёртке остаются только побочные эффекты: ФС, сеть, git,
   дочерние процессы — поэтому она автотестами не покрывается. Каталог `scripts/` подключён к
   линту корневым `eslint.config.mjs`; CI переведён на Node 22 (совпадает с `.nvmrc` и `engines`)
   и получил шаг `pnpm test:scripts`.

4. **Схема стенда:**

   | Что              | Значение                                                                     |
   | ---------------- | ---------------------------------------------------------------------------- |
   | Postgres         | один общий контейнер на `${DB_HOST_PORT:-5444}`, своя БД `recommends_<slug>` |
   | Порты            | основной checkout — 3000/3001, копии — первая свободная пара от 3010/3011    |
   | Адрес в браузере | `http://<slug>.localhost:<WEB_PORT>`                                         |
   | Серверные адреса | `http://127.0.0.1:<PORT>`                                                    |
   | Процессы         | API и web локально через `pnpm dev`; в Docker остаётся только БД             |

5. **Изоляция сессий.** `CORS_ORIGIN` генерируется списком адресов стенда
   (`<slug>.localhost`, `localhost` и `127.0.0.1` на том же web-порту, с дедупликацией), чтобы
   привычный заход на `localhost:<WEB_PORT>` или `127.0.0.1:<WEB_PORT>` не давал молчаливых
   ошибок CORS. В `apps/web/next.config.ts` добавлен
   `allowedDevOrigins: ['localhost', '127.0.0.1', '*.localhost']` — без него dev-сервер Next
   отклоняет запросы к `/_next/*` со slug-хоста.

6. **Параметризация `docker-compose.yml`.** Порты публикации вынесены в переменные с текущими
   значениями по умолчанию: `${DB_HOST_PORT:-5444}`, `${API_PORT:-3001}`, `${WEB_PORT:-3000}`.
   `.env.example` приведён к реальности: порт БД 5444, `POSTGRES_DB="recommends"` вместо
   `"nexst"`, добавлены `API_PORT`, `WEB_PORT`, `DB_HOST_PORT`, `CORS_ORIGIN`.

7. **Фиксированные dev-заглушки плюс guard.** `apps/api/src/config/env.ts` при
   `NODE_ENV=production` отклоняет известные dev-значения `JWT_SECRET` и `JWT_REFRESH_SECRET`.

### Границы решения

Эти границы важнее самой схемы — без них сгенерированный `.env` создаёт ложные ожидания.

- **Схема покрывает только локальный запуск (`pnpm dev`) и сервис `db` в compose.** Полный стек
  `docker compose up` (сервисы `api` и `web`) остаётся на своей БД `recommends` и внутренних
  портах 3000/3001: у сервиса `api` жёстко задан `DATABASE_URL: …@db:5432/recommends`, который
  значение из `.env` не переопределяет, а блоки `environment` фиксируют внутри контейнеров
  `API_PORT: 3001` и `WEB_PORT: 3000` — dev-команды приложений читают именно эти переменные, и
  без фиксации порт копии из `.env` увёл бы процессы мимо маппинга `${API_PORT}:3001` /
  `${WEB_PORT}:3000`. Из `.env` compose берёт только порты публикации на хосте.
- **Guard из пункта 7 узкий, его эффект не стоит переоценивать.** Он проверяет только два
  секрета API. `NEXTAUTH_SECRET` в `apps/web/src/lib/env.ts` остаётся без такой проверки, а
  `docker-compose.prod.yml` и так требует все секреты через `${VAR:?…}`. Реальная зона действия
  guard'а — прямой запуск `node dist/main` с продакшен-`NODE_ENV` и забытыми заглушками.
  Dev-стек `docker compose up` не затронут: сервис `api` не выставляет `NODE_ENV`, а
  `docker/api.dev.Dockerfile` не содержит `NODE_ENV=production`.
- **Slug-хост — только для браузера.** Серверные запросы (Next server-side, e2e-хелперы) должны
  идти на `127.0.0.1`, иначе поведение зависит от резолва `::1` и от того, что API слушает
  только IPv4.
- **Одновременный прогон e2e в двух копиях невозможен**: mock-сервер Telegram слушает
  фиксированный порт `4310`.
- **Основной checkout сохраняет исторические значения**: БД `recommends`, хост `localhost`,
  порты 3000/3001.

Практическая сторона — в гайде [worktree-dev.md](../guides/worktree-dev.md).

## Последствия

### Положительные

- Свежая копия репозитория доводится до рабочего стенда одной командой `pnpm setup:worktree`,
  после которой `pnpm dev` просто работает.
- Несколько копий работают одновременно: разные порты, разные базы, независимые сессии.
- Корневой `.env` стал реальным единым источником переменных для dev — исчезло расхождение между
  «что написано в `.env`» и «что читают приложения».
- `.env.example` и `docker-compose.yml` перестали врать про порт БД и имя базы.
- Каталог `scripts/` попал под линт и тесты, а CI перестал расходиться с `.nvmrc` по версии Node.

### Отрицательные / компромиссы

- Порты копии не предсказуемы заранее — их надо смотреть в сгенерированном `.env` или в выводе
  команды подготовки.
- Копии делят один инстанс Postgres: его остановка или пересоздание volume задевает все копии
  сразу, а удаление worktree не удаляет его базу — базы `recommends_<slug>` накапливаются и
  чистятся вручную.
- Dev-секреты одинаковы во всех копиях — это сознательное отклонение от критерия issue #31
  «генерировать новые секреты», компенсированное guard'ом с узкой зоной действия.
- Появился второй «режим правды» о портах: локальный запуск берёт их из `.env`, а полный
  compose-стек живёт по своим правилам — разницу приходится держать в голове и в документации.
- `dependsOn: ["^build"]` у задачи `dev` добавляет сборку общих пакетов перед каждым стартом
  `pnpm dev` (с кэшем Turborepo это быстро, но не бесплатно).

### Риски

- Подбор порта проверяет занятость в момент запуска команды: если две копии готовятся строго
  параллельно, а `.env` ещё не записан ни в одной, теоретически возможна гонка. На практике
  подготовка выполняется последовательно.
- `*.localhost` резолвится не во всех окружениях одинаково; если DNS-резолвер не отдаёт петлевой
  адрес для таких имён, изоляцию сессий придётся обеспечивать записями в `/etc/hosts`.
- Фиксированный порт `4310` у mock-сервера Telegram остаётся источником конфликтов при
  параллельной работе с e2e — снимается переводом мока на `listen(0)`.
