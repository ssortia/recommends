# ADR-015: Отдельная таблица `SourcePreference` для описания интересов по источнику

**Статус:** Принято
**Дата:** 2026-07-14

---

## Контекст

Issue #21 требует, чтобы пользователь мог задать отдельное текстовое описание интересов для
конкретного источника — в дополнение к общему описанию интересов из #12 (ADR-014, таблица
`user_preferences`, 1:1 с `User`). Пустое значение означает «используется только общее описание»;
при наличии значения оно имеет приоритет над общим при будущей AI-оценке релевантности статей
(сам scoring-модуль в кодовой базе пока не существует — правило приоритета фиксируется здесь как
поведение на будущее).

В отличие от общего описания, здесь нужна не одна запись на пользователя, а пара
«пользователь + источник»: `user_preferences` (1:1 с `User`) для этого не подходит по форме
данных.

---

## Рассмотренные варианты

- **Колонка в `user_preferences`.** Не подходит по форме данных: `user_preferences` — 1:1 с
  `User`, а описание интересов по источнику — это пара «пользователь + источник» (много записей
  на одного пользователя, по одной на каждый источник).
- **Поле на `UserSource`.** `UserSource` (модуль `sources`, ADR-007) — таблица подписок; хранение
  в ней preference-данных смешало бы домен подписок с доменом персонализации подбора, а сама
  запись `UserSource` удаляется при отписке — вместе с ней потерялось бы и описание интересов,
  что нежелательно (см. «Последствия» ниже).
- **Отдельная таблица `source_preferences` (модель `SourcePreference`).** Изолирует
  preference-данные по источнику в том же домене, что и `user_preferences` (модуль
  `preferences`), по образцу ADR-014. Составной первичный ключ `(userId, sourceId)`, лениво
  создаваемая запись, независимый жизненный цикл от `UserSource`.

Выбран третий вариант.

---

## Решение

1. **Таблица `source_preferences`** (модель `SourcePreference`) — составной первичный ключ
   `(userId, sourceId)`, `onDelete: Cascade` на оба FK (`User`, `Source`).
   `interestsDescription String? @db.VarChar(1000)` — тот же лимит, что и у общего описания
   (ADR-014).

2. **Ленивое создание записи**, как и у `UserPreferences`: запись не создаётся при подписке на
   источник — только при первом сохранении индивидуального описания (`upsert`).
   `GET /preferences/sources/:sourceId` для пары без записи возвращает
   `{ interestsDescription: null }`.

3. **Проверка подписки, а не владения записью.** Модуль `preferences` читает
   `UserSourcesRepository` из `SourcesModule` (экспортирован для этого) только для проверки, что
   пользователь подписан на `sourceId` — иначе 404. `SourcesModule` не знает о `preferences`,
   циклической зависимости нет.

4. **Независимость от `UserSource`.** FK `SourcePreference.sourceId` ссылается на `Source`, а не
   на `UserSource`. При отписке (`UserSourcesRepository.delete`) запись `source_preferences` не
   удаляется автоматически. Это осознанное решение: если пользователь подпишется на тот же
   источник повторно, его прежнее индивидуальное описание интересов восстановится, а не потеряется
   безвозвратно. Запись `source_preferences` каскадно удаляется только при удалении самого
   `User` или `Source`.

5. **Эндпоинты.** `GET /preferences/sources/:sourceId` и `PATCH /preferences/sources/:sourceId`,
   под теми же `JwtAuthGuard` + `VerifiedGuard`, что и общий эндпоинт `/preferences`; 404, если
   пользователь не подписан на `sourceId`.

6. **Именование в единственном числе.** В отличие от `UserPreferences` (ADR-014, множественное
   число — одна запись объединяет все preference-поля пользователя), новая модель называется
   `SourcePreference` в единственном числе: у пользователя может быть много таких записей (по
   одной на источник), и обратная связь читается как `SourcePreference[]` — множественное число
   уже выражено массивом, а не именем типа. Это осознанное расхождение в конвенции именования
   между двумя моделями одного домена, отражающее разницу в кардинальности (1:1 vs 1:N).

---

## Последствия

### Положительные

- Индивидуальное описание интересов физически и логически отделено от таблицы подписок
  (`UserSource`) и от общего описания (`UserPreferences`), но остаётся в одном домене
  `preferences` — единообразно с ADR-014.
- Повторная подписка на источник восстанавливает ранее сохранённое индивидуальное описание —
  пользователю не нужно вводить его заново.
- Расширение `SourcesModule` ограничено одним `exports: [UserSourcesRepository]`, без
  циклической зависимости между `sources` и `preferences`.

### Отрицательные / компромиссы

- Запись `source_preferences` переживает отписку от источника — при большом числе
  подписок/отписок таблица накапливает «осиротевшие» (по смыслу подписки, не по FK) записи,
  которые физически не удаляются, пока существует пара `User`/`Source`. Такое поведение — осознанный
  выбор в пользу удобства пользователя, но потребует отдельной политики очистки, если объём
  данных станет проблемой.
- Правило приоритета «описание источника → иначе общее описание» пока нигде не применяется в
  коде (нет AI/scoring-модуля) — зафиксировано только здесь и в комментариях, риск того, что при
  реализации scoring-модуля правило будет забыто или реализовано иначе.
- Расхождение в числе (`SourcePreference` vs `UserPreferences`) в рамках одного домена требует
  явного объяснения новым участникам — почему две похожие модели названы по-разному
  (см. пункт 6 решения).
